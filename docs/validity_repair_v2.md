Where this document conflicts with v5, the v5 specification governs.


## Status

The July 2026 rolling checkpoints, backtest tables, figures, and manuscript results are **legacy/provisional**. They remain in the repository for auditability but must not be used as confirmed empirical results.

The corrected pipeline is versioned as `sv-filter-v2`. New artifacts belong under `checkpoints/v2/` and `outputs/v2/`.

## Why a full re-run is required

The original pipeline contained errors that materially affect tail-risk forecasts and model comparisons:

1. the SV latent volatility state was stale between 42-day MCMC refits;
2. leverage parameter `rho` was omitted from predictive simulation;
3. Student-t innovations were not variance-standardized and `nu > 2` was not actually enforced;
4. Acerbi-Szekely Test 2 used average ES instead of observation-specific `ES_t`;
5. EGARCH was fitted without the asymmetric term;
6. GARCH-family benchmarks were Gaussian-only, creating an unfair comparison with SV-t;
7. runner window settings and checkpoint identity were not fully configuration-safe.

Because the saved v1 forecasts were generated by the affected code, they cannot be repaired by recomputing only the final backtest tables. Forecasts must be regenerated from scratch.

## Corrected forecasting protocol

For each commodity and rolling forecast date:

1. Use the preceding `W` observations as the estimation window.
2. Re-estimate SV structural parameters by MCMC every `refit_every` trading days (default 42).
3. Between structural-parameter refits, propagate the latent log-volatility state one day forward using posterior particles.
4. Draw the one-step predictive return distribution **before** using the forecast date's realized return.
5. Compute VaR and ES from the same predictive sample.
6. After the forecast is recorded, condition the latent state on the newly realized return for use on the next date.
7. For leverage variants, use the same volatility innovation in the return shock through `rho`.
8. For Student-t variants, enforce `nu > 2` and standardize t innovations to unit variance.

This ordering is designed to avoid look-ahead: the return observed on date `t` updates the state for the `t+1` forecast, not the forecast already issued for date `t`.

## Primary model set

### Bayesian stochastic volatility

- SV-Gaussian
- SV-t
- SV-Leverage
- SV-t-Leverage

### Benchmarks

- GARCH-Normal
- GARCH-t
- asymmetric EGARCH-Normal (`o=1`)
- asymmetric EGARCH-t (`o=1`)
- Ornstein-Uhlenbeck
- Historical Simulation

Adding Student-t GARCH-family models separates the value of stochastic latent volatility from the value of simply allowing heavy-tailed innovations.

## Primary configuration

- Rolling window: `W = 1000`
- SV structural refit interval: 42 trading days
- VaR/ES levels: 1% and 5%
- Posterior predictive draws per SV forecast: 20,000 or more
- Production NUTS target acceptance: 0.95
- Random seeds: deterministic and date-indexed as implemented in `src/sv_model.py`

Every configuration is written to a distinct checkpoint namespace. A run with a different window, refit interval, model version, or predictive sample size must not reuse another configuration's SV checkpoint.

## Backtesting

The primary tests are evaluated separately at 1% and 5%:

1. Kupiec unconditional coverage;
2. Christoffersen conditional coverage;
3. Acerbi-Szekely Test 2 for ES.

Christoffersen independence is retained as a separate diagnostic rather than silently counted as an additional primary test.

Acerbi-Szekely Test 2 uses the time-varying statistic

`Z2 = sum_t [r_t I_t / (T * alpha * ES_t)] + 1`,

with each observation's own ES forecast in the denominator.

## Required robustness checks

The following pre-specified checks remain mandatory after the corrected primary run:

1. rolling-window sensitivity: `W = 750, 1000, 1250`;
2. cocoa with the three flagged 2024 dates excluded;
3. ICCO cocoa prices in place of the primary cocoa futures series;
4. WTI in place of Brent;
5. SV prior sensitivity for persistence/volatility parameters;
6. GARCH-order sensitivity including `(p,q) = (1,2)` and `(2,1)`.

The GARCH implementation now applies stationarity checks across all fitted alpha/beta coefficients so the alternative-order runs do not silently use unstable fits.
